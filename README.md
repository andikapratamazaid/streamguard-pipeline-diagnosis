# StreamGuard: Streaming Pipeline Reliability and Incident Diagnosis

A data engineering support case study. StreamGuard simulates the work of a
support and reliability team for a streaming data platform: it generates
synthetic telemetry and incident data, detects anomalies in the telemetry,
diagnoses incidents with an explainable rule-based engine, and analyzes
resolution performance across the five problem categories that dominate
streaming platform support:

1. Streaming Pipeline Failure
2. Cluster Health Degradation
3. Indexing Performance Bottleneck
4. Data Ingestion Failure
5. Configuration Error

> **Honesty note: all data in this project is synthetic.** The telemetry and
> the 384 incidents were generated by seeded Python scripts in `data/`,
> modeled on typical streaming data platform behavior (Kafka-style pipelines,
> cluster resource metrics, indexing latency, ingestion error streams). This
> is not production data from any company, and the results describe the
> simulation, not a real service. Every number quoted below was computed by
> the scripts in this repository from the generated dataset.

## Key results (computed, seed 42)

| Metric | Result |
|---|---|
| Incidents in the 90 day window (2026-01-01 to 2026-03-31) | 384 |
| Telemetry points (6 pipelines, hourly, 90 days) | 12,960 |
| Overall MTTR | 157.77 minutes (median 124) |
| Mean CSAT | 4.75 out of 5 (83.85% of incidents rated 5) |
| Diagnosis engine accuracy | 98.96% (380 of 384) |
| Anomaly detection coverage | 97.92% (376 of 384 incidents matched) |
| Escalation rate | 24.48% (94 incidents) |

### Per category

| Category | Incidents | Share | MTTR (min) | CSAT mean | Engine accuracy | Detection coverage |
|---|---|---|---|---|---|---|
| Streaming Pipeline Failure | 110 | 28.65% | 111.77 | 4.81 | 99.09% | 96.36% |
| Cluster Health Degradation | 75 | 19.53% | 269.0 | 4.75 | 100% | 100% |
| Indexing Performance Bottleneck | 70 | 18.23% | 173.6 | 4.59 | 98.57% | 100% |
| Data Ingestion Failure | 89 | 23.18% | 147.9 | 4.73 | 98.88% | 98.88% |
| Configuration Error | 40 | 10.42% | 69.92 | 4.9 | 97.5% | 92.5% |

Reading the results honestly:

- The engine makes only 4 mistakes in 384 incidents, each a single
  cross-category confusion (for example one Streaming Pipeline Failure with
  an unusual symptom mix classified as Data Ingestion Failure). The high
  accuracy reflects the simulation design: symptom signatures are sampled
  per category with light cross-category noise, so the signal is strong.
  On real production data, with messier symptoms, accuracy would be lower.
- Detection misses concentrate in Configuration Error (92.5% coverage):
  some configuration incidents present only through a recent change record,
  which leaves no telemetry deviation to detect. That is a realistic blind
  spot and an argument for change-log alerting, covered in runbook RB-05.
- Cluster Health Degradation is the slowest category to resolve (269.0
  minutes mean) because it needs infrastructure action; Configuration Error
  is the fastest (69.92 minutes) because it usually ends with a rollback.
- 14 root causes recur 15 or more times and account for 83.33% of all
  incidents. The top one, consumer group rebalance storms caused by short
  session timeouts, alone accounts for 31 incidents. Permanent fixes for
  recurring causes beat faster handling of individual incidents.
- CSAT is resolution-time sensitive: incidents closed within 120 minutes
  average 4.81, incidents taking over 300 minutes average 4.59.

## Architecture

```
sg_common.py                  Shared vocabulary: categories, symptoms,
                              signatures, root causes, resolution steps
data/
  generate_incidents.py       Seeded generator for the 384 labeled incidents
  generate_telemetry.py       Seeded hourly telemetry for 6 pipelines,
                              with deviations injected during incident windows
  incidents.csv               The labeled incident dataset
  telemetry.csv               The telemetry time series (12,960 rows)
engine/
  diagnosis_engine.py         Rule-based diagnosis: symptoms to category,
                              root causes, and resolution steps
  evaluate_engine.py          Accuracy evaluation against the labels
detection/
  anomaly_detection.py        Rolling z-score plus threshold detection,
                              matched back to incident windows
analysis/
  run_analysis.py             MTTR, CSAT, escalation, recurrence analytics
  findings.md                 Findings document generated from the numbers
  charts/                     PNG charts used by the dashboard
runbooks/                     One resolution playbook per category (RB-01..05)
dashboard/
  build_dashboard.py          Builds the self-contained HTML dashboard
  streamguard_dashboard.html  KPIs, charts, and an interactive diagnosis demo
output/                       Machine-readable results (JSON)
tests/                        unittest suite (standard library only)
```

## How to run

Everything runs with Python 3 and the standard library, except chart
rendering which uses matplotlib.

```bash
# 1. Generate the datasets (fixed seed 42, reproducible)
python3 data/generate_incidents.py
python3 data/generate_telemetry.py

# 2. Evaluate the diagnosis engine against the labeled incidents
python3 engine/evaluate_engine.py

# 3. Run anomaly detection over the telemetry
python3 detection/anomaly_detection.py

# 4. Run the analytics (charts, findings.md, analysis_results.json)
python3 analysis/run_analysis.py

# 5. Build the dashboard, then open it in a browser
python3 dashboard/build_dashboard.py
# open dashboard/streamguard_dashboard.html

# 6. Run the tests
python3 -m unittest discover -s tests
```

## The diagnosis engine

The engine is deliberately rule-based and explainable rather than a black
box model. Each of the 16 observable symptoms awards points to one or more
categories (for example consumer lag spike gives 3 points to Streaming
Pipeline Failure and 1 to Cluster Health Degradation). The highest scoring
category wins; confidence combines the winner's share of total points with
its margin over the runner-up. Likely root causes are ranked from symptom
hints, and the recommended steps come straight from the runbook library.
The dashboard demo runs the identical weights in JavaScript, serialized
from the Python engine at build time, so the two implementations cannot
drift apart.
